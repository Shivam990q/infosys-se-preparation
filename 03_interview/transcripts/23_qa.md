## Transcript 1: Computer Science / IT Candidate (Technical Architecture Defense)

**Candidate:** Rahul (B.Tech CSE, 8.2 CGPA)  
**Outcome:** **SELECTED (Offered SE with DSE Upgrade Recommendation)**

> **Interviewer:** *"Hello Rahul. I see you built an 'E-Commerce Microservices Platform' as your final year project. Can you sketch out how authentication works between your services?"*  
> 
> **Candidate:** *"Sure, Sir. In our system, we decoupled authentication into a dedicated Auth Service. When a user logs in, the Auth Service validates their credentials against a PostgreSQL database using bcrypt hashing. If valid, it generates a cryptographically signed JSON Web Token (JWT) containing the user ID, role, and a 15-minute expiration timestamp.  
> When the client calls downstream services—like the Order Service or Payment Service—it sends this JWT in the `Authorization: Bearer <token>` HTTP header. An API Gateway intercepts the request, verifies the token's RSA public key signature without querying the database again, and routes the request. This avoids a database bottleneck on every single API call."*  
> 
> **Interviewer:** *"Good. What happens if a user clicks 'Buy Now' twice in rapid succession on an unstable 3G connection? How do you prevent double debiting?"*  
> 
> **Candidate:** *"That is a classic idempotency problem, Sir. We solve it at both the API Gateway and database levels:  
> 1. When the user opens the checkout screen, the client generates a unique UUID `idempotency_key` and passes it in the checkout payload.  
> 2. The Payment Service checks Redis with `SET NX` using this key. If the key already exists, subsequent duplicate requests within a 60-second window are blocked immediately.  
> 3. At the database layer, the `transaction_reference_id` column has a `UNIQUE` constraint, so even if a race condition slips past cache, the second `INSERT` triggers a duplicate key exception and triggers an automatic transaction rollback."*  
> 
> **Interviewer:** *"Excellent. Quick question on databases: In MySQL, what is the internal data structure used for InnoDB indexes, and why not a Hash index?"*  
> 
> **Candidate:** *"InnoDB uses a **B+ Tree** data structure. We prefer B+ Trees over Hash indexes because Hash indexes only support point lookups ($O(1)$ equality checks like `WHERE id = 10`), but cannot perform range scans or sorting (`WHERE age BETWEEN 20 AND 30` or `ORDER BY created_at`). In a B+ Tree, all leaf nodes are linked sequentially in a doubly-linked list, allowing high-performance range traversals in $O(\log N)$ time."*

## Transcript 2: Non-CS Candidate (Mechanical / Electrical Engineering Bridge)

**Candidate:** Priya (B.Tech Mechanical Engineering, 7.6 CGPA)  
**Outcome:** **SELECTED (Offered SE)**

> **Interviewer:** *"Priya, you have a 7.6 CGPA in Mechanical Engineering. Why do you want to join Infosys as a Systems Engineer instead of pursuing Tata Motors or Larsen & Toubro?"*  
> 
> **Candidate:** *"Sir, throughout my coursework in thermodynamics and fluid mechanics, the most rewarding phase for me was always numerical modeling. In my 3rd year, when analyzing heat dissipation across engine fins, manual calculations took days. I wrote a Python script using NumPy to simulate the differential equations in minutes.  
> That experience made me realize that software is the fundamental leverage tool of the modern world. Over the past 14 months, I committed to formal computer science foundations: I mastered Python, completed Data Structures and Algorithms on LeetCode solving over 150 problems, and built a full-stack Inventory Management system using Flask and SQLite.  
> Engineering taught me first-principles problem solving and rigorous mathematical discipline; software provides the medium to build scalable solutions. Infosys has the world's best training infrastructure at Mysore to help engineers from multidisciplinary backgrounds transition into enterprise software professionals."*  
> 
> **Interviewer:** *"That's a very clear answer. Can you tell me what happens under the hood when a recursive function executes in memory?"*  
> 
> **Candidate:** *"Yes, Sir. When a function calls itself, the operating system allocates a new **Stack Frame** on the Call Stack in RAM. This frame stores the function's local variables, arguments, and the return address pointing back to the caller instruction.  
> Each recursive call pushes another frame onto the stack until the **Base Condition** is met. Once the base condition returns, the stack unwinds, popping frames one by one in Last-In, First-Out (LIFO) order. If the programmer forgets the base condition or recurses too deeply, the allocated call stack space exceeds memory limits, throwing a `StackOverflowError`."*

## Transcript 4: Answering When You Don't Know the Answer (The Panic Trap)

**Scenario:** The interviewer asks an obscure question to test how the candidate reacts under uncertainty.

> **Interviewer:** *"Can you explain the difference between the Raft and Paxos consensus algorithms in distributed databases?"*  
> 
> **Wrong Approach (Fatal Mistake):**  
> ❌ *"Sir, Paxos is used for SQL databases and Raft is used for NoSQL databases..."* (Bluffing / making up facts = Instant Rejection).  
> 
> **Right Approach (Professional Defense):**  
> ✔️ *"Sir, I have studied distributed database basics such as the CAP theorem, two-phase commit (2PC), and eventual consistency, but I have not implemented Raft or Paxos in depth.  
> If I had to reason from first principles, I understand that both are distributed consensus protocols used to elect leader nodes and synchronize distributed state logs across server clusters to maintain consistency during network partitions. I would be eager to explore their exact mathematical state transitions in our Mysore training."*  
> 
> *Key takeaway: Acknowledge boundaries honestly, demonstrate adjacent foundational knowledge, and express proactive curiosity.*
